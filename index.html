Personal job search infrastructure · self-hosted · yours alone

Set up your own Job Application Agent

A personal pipeline that watches for jobs, scores them against your own profile, and tells you which ones are worth your time — so you stop reading job boards and start reading a shortlist.

Collectalert emails, job APIs, manual paste
→
Classifynormalise, dedupe, sort
→
ScoreAI evaluation against your profile
→
Recommendshortlist, sheet, Telegram
Time: 1–3 hours, split however you like
Cost: free tiers, plus a few dollars a month if you turn on AI scoring
You'll need: a terminal, a GitHub account, your CV

What it will never do: write a cover letter, tailor your CV, answer a screening question, or submit anything on your behalf. It finds and ranks. You still do the applying.

Before you start — this is a personal system, not a shared one

Every part of this project is scoped to one person: one database holds one candidate profile, one Gmail inbox is read for alerts, one set of API keys pays for one person's AI usage. It was not built to serve two people from one deployment.

That means setting this up for yourself is not a matter of getting added to someone else's Supabase project, Vercel account, or Google Cloud project. You'll create your own copy of everything in this guide — your own database, your own Google Cloud project, your own API keys, and your own candidate files describing your background. Nothing here is shared, and nothing you enter is visible to anyone else's copy of the system.

00

Get the code onto your machine

Required ~10 min

The original copy of this project lives in a private repository, and its git history carries personal information that belongs to whoever built it — so the right move isn't to be added as a collaborator on that exact repo. Instead, start a clean repository of your own from a plain copy of the code (no .git history, no node_modules, no .env.local).

Get a clean copy

Ask whoever shared this guide with you for a zipped copy of the project folder, or download one from wherever they've made it available. Unzip it somewhere on your computer — for example ~/Projects/job-application-agent or C:\Projects\job-application-agent.

Create your own repository

On github.com/new, create a new repository — private is fine, since it's about to hold your CV and personal details. Then, from inside your unzipped folder:

Terminal — inside your project folder
bash / zsh / PowerShell
git init
git add .
git commit -m "Initial commit"
git branch -M main
git remote add origin https://github.com/<your-username>/<your-repo-name>.git
git push -u origin main

Prefer no command line for this bit?

GitHub's web uploader works too: create the empty repository, click Add file → Upload files, and drag the whole folder in (minus anything already excluded by .gitignore, like node_modules). You'll still need a terminal from Phase 1 onward.

01

Install prerequisites & dependencies

Required ~10 min

Install Node.js

You need Node 20.11 or newer. Download the LTS installer from nodejs.org and run it — npm comes bundled with it, so there's nothing extra to install.

Terminal — check the version
bash / zsh / PowerShell
node -v
# expect v20.11.0 or higher

Install the project's dependencies

Terminal — inside your project folder
bash / zsh / PowerShell
npm install

This reads package.json and pulls in Next.js, React, the Supabase client, and everything else the app needs.

02

Create your database

Required ~15 min

The app stores everything — jobs, your profile, scores, decisions — in a Postgres database. Supabase's free tier is what this project was built and tested against, so it's the easiest route in.

Create the project

Sign up at supabase.com/dashboard and create a new project. Pick any name and a region close to you. Save the database password it asks you to set — you'll need it in a moment.

Start your environment file

Back in your project folder, copy the example environment file. This is the file that holds every secret the app uses, and it's already excluded from git.

Terminal
macOS / Linux
cp .env.example .env.local
Windows PowerShell
Copy-Item .env.example .env.local

Fill in four values

Open .env.local in a text editor. From your Supabase project's dashboard, fill in:

VariableWhere to find it
DATABASE_URLProject Settings → Database → Connection string → Session pooler. Copy the whole string from the dashboard rather than typing it by hand — the hostname's prefix (aws-0, aws-1…) is assigned per project, and guessing it produces a confusing "tenant not found" error that looks like a DNS problem.
NEXT_PUBLIC_SUPABASE_URLProject Settings → API
NEXT_PUBLIC_SUPABASE_ANON_KEYProject Settings → API — the publishable/anon key. Safe to expose in the browser.
SUPABASE_SERVICE_ROLE_KEYProject Settings → API Keys — the secret service_role key. This one bypasses all database security rules — never share it, never put it in anything that ships to a browser.

Set up the schema

Terminal
bash / zsh / PowerShell
npm run db:migrate   # creates all the tables
npm run db:seed      # adds starter config + a few sample jobs

A successful seed prints a line like Seeded. sources=5 saved_searches=8 jobs=5. Those five sample jobs are clearly fictional (fake employers like "Northwind" or "Cobalt") — they're there purely so you have something to look at before any real source is connected.

03

Tell it who you are

Required ~20 min

The single most important rule in this whole project: the system never invents anything about you. Every score, every recommendation, every "missing requirement" it flags comes only from what's written in four files in the candidate/ folder. If your CV doesn't mention a skill, the system won't assume you have it — it'll just mark that requirement unmet.

FileHolds
candidate/candidate_profile.jsonYour background — education, work history, skills, licences, certifications.
candidate/job_preferences.jsonThe roles, locations and working arrangements you're actually looking for.
candidate/projects.jsonPersonal or academic projects worth showing as evidence — kept clearly separate from paid employment.
candidate/CV.pdfYour actual CV, for anything the JSON doesn't capture in full.

Open each JSON file — the ones already in the folder are a real, filled-in example, so use their structure as a template and replace every field with your own information. Swap in your own CV.pdf too.

Be thorough here

Because nothing is invented on your behalf, an accurate score depends entirely on how complete these files are. A skill you have but forgot to list is a skill the system will treat as a gap. Ten minutes of extra detail here is worth more than any setting later in this guide.

Terminal
bash / zsh / PowerShell
npm run profile:load
# writes your JSON files into the database as candidate_profile version 1

Re-run this command any time you update your profile — it validates the files and stores a new version.

04

Generate your cron secret

Required ~2 min

Once this is deployed (Phase 8), something needs to prove to the app that a scheduled request really is the scheduler and not a stranger poking the internet. That's CRON_SECRET — a random string only you and your deployment know. Generate one now so it's ready:

Terminal — works the same on every OS, since it just uses Node
bash / zsh / PowerShell
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"

Paste the result into .env.local as CRON_SECRET=. It needs to be at least 16 characters, so this 64-character version comfortably clears that.

Run it locally

Required ~5 min
Terminal
bash / zsh / PowerShell

Open http://localhost:3000 — you should see a dashboard listing the sample jobs from Phase 2.

Check the health endpoint

Terminal — in a second window, while npm run dev is still running
macOS / Linux
curl -s http://localhost:3000/api/health
Windows PowerShell

A healthy response reports HTTP 200, "status":"healthy", the number of migrations applied, and your active profile version. If any of those look wrong, re-check Phases 2 and 3 before moving on.

Checkpoint You now have a fully working system running on your own machine, scoring nothing yet, watching nothing yet — just correctly wired up. Everything from here makes it useful and automatic rather than just alive.
06

Turn on AI scoring

Recommended The only step that spends money ~10 min

Every other part of this system is free to run. Scoring a job against your profile calls an AI model, and that's the one line item with a real bill attached — so it's opt-in, and capped.

Get a key

Create an API key at platform.claude.com and add it to .env.local as ANTHROPIC_API_KEY. Without this key, evaluation skips cleanly — collection, the dashboard and everything else keep working, jobs simply stay unscored.

Set your own spending limits

Two variables cap what this can spend, and both default conservatively — but set them to match what you're actually comfortable spending, since the defaults know nothing about your actual budget:

AI_MONTHLY_BUDGET_USDhard monthly ceiling
AI_RUN_CEILING_USDcap per single run

When the monthly figure is reached, scoring stops for the rest of the month — collection and notifications carry on regardless, new jobs just arrive unscored until the next month. As a rough sense of scale, scoring twenty jobs a day at the cheaper "triage" tier has historically landed around 15–20 cents a day, so well under $10 over a month — but treat that as a ballpark from one point in time, not a quote: model pricing changes, and your own ceiling is what actually protects you, not this number.

07

Bring in real jobs

Required — pick at least one 5 min to 30 min, depending which

Every job source is independent and every adapter skips cleanly when it has no credentials — so add as many or as few as you like, starting with whichever is easiest for you.

Zero setup

Paste a job in by hand

The dashboard has a manual capture form. Paste in a job posting you found yourself and it runs through the same scoring pipeline as everything else. Good for proving the system works before configuring anything.

Most coverage

Gmail job alerts

Indeed and LinkedIn have no API a personal project can legitimately use — so instead, this reads the alert emails they already send to your own inbox. See the walkthrough below.

Free API keys

Reed / Careerjet / Jooble

UK-focused job search APIs with free tiers. Sign up, paste a key into .env.local, done — no OAuth involved.

Option: Gmail job alerts (the fiddliest, most rewarding one)

This is a genuine OAuth setup, and it has one non-obvious trap, so read this section fully before starting. It only reads mail — gmail.readonly is the only scope this part needs, and nothing in the code can send, label, or delete anything through it.

The 7-day trap

Google issues a refresh token that expires every 7 days for as long as your Google Cloud project's OAuth consent screen is left in "Testing" mode. Left alone, this makes collection quietly start failing with invalid_grant roughly once a week, looking exactly like something broke. Publish the app to production instead (step 5 below) — for a single-user personal project this is one extra click, triggers an "unverified app" warning you click through, and the token then simply doesn't expire.

  1. At console.cloud.google.com, create a new project (any name).
  2. Search Gmail API in the top search bar and click Enable.
  3. APIs & Services → OAuth consent screen. Choose External (the only option for a personal, non-Workspace Google account), fill in an app name and your own email as the support/developer contact.
  4. Data access → Add or remove scopes — add .../auth/gmail.readonly. (If you're also setting up the Google Sheet in Phase 9, add .../auth/spreadsheets at the same time — it saves repeating this later.)
  5. Go to console.cloud.google.com/auth/audience and click Publish app. This is the step that defuses the 7-day trap above.
  6. APIs & Services → Credentials → Create credentials → OAuth client ID. Application type Web application (not Desktop — a web client lets you set the redirect URI explicitly). Under Authorised redirect URIs add exactly http://localhost — no trailing slash, no port. Save the Client ID and Client secret it gives you.
  7. Add GMAIL_CLIENT_ID and GMAIL_CLIENT_SECRET to .env.local.
Terminal — this opens a browser consent screen for you
bash / zsh / PowerShell
npm run google:auth

Sign in with the Google account whose alerts you want read, approve the permissions, and the script writes GMAIL_REFRESH_TOKEN (and GOOGLE_REFRESH_TOKEN) into .env.local for you. If you see "Google hasn't verified this app," that's expected for your own unpublished-to-the-world app — click Advanced → Go to (your app name) (unsafe).

Terminal
bash / zsh / PowerShell
npm run collect

Look for emailsIngested greater than zero in the output — that's confirmation the app really did read your inbox. The full walkthrough, with every error message explained, ships in GMAIL_OAUTH_SETUP.md in the repo if you hit anything not covered here.

Option: aggregator APIs

REED_API_KEYreed.co.uk/developers
CAREERJET_AFFILIATE_IDcareerjet.co.uk/partners
JOOBLE_API_KEYjooble.org/api/about

Free signups, each gives you a key to paste into .env.local. Note that a key alone isn't quite enough for these three specifically — they're deliberately disabled by default so an old key can't silently switch a source back on. To use one, also list it by name in ENABLE_SOURCES (see the comments in .env.example).

What about apprenticeship listings?

The codebase includes an adapter for the UK's official "Find an apprenticeship" feed, but it ships disabled — a choice made by whoever set this instance up originally for their own search, not a limitation of the code. If apprenticeships are relevant to you, it's there to re-enable; search the repo for findapprenticeship to see where.

08

Deploy it so it runs every day

Recommended ~20 min

Everything so far runs only while your laptop is open and npm run dev is running. Deploying to Vercel's free Hobby plan is what lets it collect, score and notify you automatically, every day, without you doing anything.

Push and import

Push your repository to GitHub if you haven't already (Phase 0), then go to vercel.com/new and import it. Vercel detects Next.js automatically — no configuration needed there.

Add every environment variable

In Project → Settings → Environment Variables, add everything you've collected in .env.local so far, set for the Production environment (scheduled jobs only ever run against production):

DATABASE_URL
NEXT_PUBLIC_SUPABASE_URL
NEXT_PUBLIC_SUPABASE_ANON_KEY
SUPABASE_SERVICE_ROLE_KEY
CRON_SECRET
ANTHROPIC_API_KEY
AI_MONTHLY_BUDGET_USD
AI_RUN_CEILING_USD
GMAIL_CLIENT_ID
GMAIL_CLIENT_SECRET
GMAIL_REFRESH_TOKEN
APP_URLyour vercel.app URL

Plus whichever optional ones from Phases 6, 7 and 9 you set up. Changing a variable only takes effect on the next deployment, so redeploy after editing any of them.

The schedule is already in the repo

vercel.json defines four daily jobs, an hour apart so each finishes before the next starts, all in UTC:

vercel.json
{
  "crons": [
    { "path": "/api/cron/collect",  "schedule": "0 5 * * *" },
    { "path": "/api/cron/evaluate", "schedule": "0 6 * * *" },
    { "path": "/api/cron/sheet",    "schedule": "0 7 * * *" },
    { "path": "/api/cron/notify",   "schedule": "0 8 * * *" }
  ]
}

Adjust the hours to taste — the free Hobby plan allows one run per day per job, firing somewhere inside its scheduled hour rather than on the exact minute.

Confirm it worked

Once deployed, check https://<your-app>.vercel.app/api/health and look at Project → Cron Jobs in the Vercel dashboard the day after your first scheduled run to see each job's status.

09

Optional extras

Optional 10–20 min each

A self-updating Google Sheet

Rather than re-running an export command, you can have a spreadsheet that rewrites itself with your current shortlist every morning. It reuses the same Google Cloud project from Phase 7 — you just need to add one more scope.

  1. APIs & Services → Library → Google Sheets API → Enable.
  2. OAuth consent screen → Data access → Add or remove scopes — add .../auth/spreadsheets alongside gmail.readonly.
  3. Re-run npm run google:auth. This step matters even if you did Gmail alerts already — a token never gains a scope after it's issued, so adding the scope in the console alone does nothing until you get a new token.
  4. Create a new blank Google Sheet, copy its URL or ID into GOOGLE_SHEET_ID in .env.local (and in Vercel, if deployed).
bash / zsh / PowerShell
npm run export -- --sheets

The sheet is fully overwritten on every run, with one exception: whatever you type into its Decision column (interested, applied, rejected…) is read back and carried across before the rewrite, matched by job rather than by row position.

Telegram notifications

  1. Message @BotFather on Telegram, send /newbot, and copy the token it gives you into TELEGRAM_BOT_TOKEN.
  2. Send your new bot any message first — a bot can't start a conversation, so until you message it, it has nowhere to reply.
  3. Open https://api.telegram.org/bot<TOKEN>/getUpdates in a browser and read result[0].message.chat.id — that's TELEGRAM_CHAT_ID.
bash / zsh / PowerShell
npm run notify -- --test

Without both variables set, notifications are skipped cleanly — nothing else in the pipeline is affected.

The Gmail application tracker

A separate piece that watches your outgoing job search mail — acknowledgements, interview invites, rejections — and moves a tracker row automatically. It runs inside Google's own Apps Script environment, not inside this app, using a script version-controlled at scripts/gmail/gmail-ai-triage.gs.

  1. In Gmail, create a filter that applies a label (e.g. Job Applications) to mail from ATS platforms (Greenhouse, Workday, Lever, SmartRecruiters…) or matching subject keywords like "application" or "interview." Don't skip the inbox — you still want to read these.
  2. Go to script.google.com (signed in as the account that receives that mail), create a new project, and paste in the contents of scripts/gmail/gmail-ai-triage.gs.
  3. Optional: get a free key at aistudio.google.com for the small number of emails plain rules can't classify, and add it under Project Settings → Script Properties as GEMINI_API_KEY. Without it, unreadable mail just stays visible and unclassified — the safe default.
  4. Run the setup() function once from the Apps Script editor and approve the permissions it asks for. This installs the triggers that check your inbox every 15 minutes.
10

Using it day to day

Ongoing

Once it's deployed and collecting, this is roughly the loop:

  • Check the self-updating Google Sheet (or run npm run export for a fresh shortlist.xlsx) — best matches first, colour-coded.
  • Mark a job interested or saved to keep it visible, or set the Decision column to applied once you've actually applied — that's the one signal the system trusts, since it never guesses that you applied from an email alone.
  • From there, replies about that job get matched automatically and move it through the tracker: acknowledged → interview → rejected/offer.
  • A daily Telegram digest, if you set it up, surfaces the strongest new matches without you having to go looking.
  • The Sheet's Status tab (or Vercel's Cron Jobs page) is the place to check when something feels stale — it timestamps the last successful run of every stage.

And to say it once more plainly: nothing here ever submits an application, sends a message, or writes anything on your behalf. It reads, scores, and tells you. The rest is still yours.

Troubleshooting

SymptomLikely causeFix
(ENOTFOUND) tenant/user … not foundWrong Supabase pooler hostname prefix in DATABASE_URL.Copy the connection string directly from the Supabase dashboard rather than editing an example by hand.
Cron runs return 503 on VercelAn environment variable the route needs is missing in Production.The response body names which one — add it and redeploy.
invalid_grant: Token has been expired or revokedYour Google Cloud OAuth consent screen is still in "Testing," so the refresh token died after 7 days.Publish the app (Phase 7, step 5), then re-run npm run google:auth.
ACCESS_TOKEN_SCOPE_INSUFFICIENTYou added a scope in Google Cloud Console, but your existing token was issued before that and never gained it.Re-run npm run google:auth — scopes are only baked in when a token is issued.
redirect_uri_mismatchThe registered redirect URI doesn't exactly match http://localhost — often a stray trailing slash.Check the OAuth client's Authorised redirect URIs in Google Cloud Console.
Collection reports adapters "skipped (no credentials)"Expected — a source with no key is meant to skip quietly rather than fail the whole run.Add that source's credentials if you want it running, or ignore it if you don't.
Evaluation isn't scoring anythingNo ANTHROPIC_API_KEY set, or the monthly budget has been reached.Add the key (Phase 6) or check AI_MONTHLY_BUDGET_USD against what's actually been spent this month.

Gmail-specific errors are covered in far more depth, with the exact console screens involved, in GMAIL_OAUTH_SETUP.md inside the repository.
